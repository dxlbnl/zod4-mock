# Playground Evolution: Towards a Complete Zod4-Mock Experience

This document outlines the current state of the `zod4-mock` Playground and proposes a roadmap for its evolution into a comprehensive tool that covers all aspects of the library.

## 🎯 Current State Assessment

The playground currently excels at **Schema Building**. It provides a high-fidelity, interactive environment to:

- **Build Zod schemas**: Create Subjects and API Schemas with a nested structure (objects, arrays).
- **Apply Modifiers**: Visual controls for `.min()`, `.max()`, `.int()`, `.optional()`, etc.
- **Real-time Preview**: Immediate feedback on generated code and mock data.
- **Code Export**: Generate a complete `world.ts` file representing the current state.

### What's missing?

`zod4-mock` is fundamentally a **seeded, relational mock data ecosystem**. The current playground focuses heavily on the "representation" (API Schemas) but under-represents the "identity" (World, Registry, and Relations).

---

## 🚀 Proposed Pillars for Evolution

### 1. Relational Modeling & Registry

The "World" concept is about multiple subjects co-existing and relating to each other.

- **Relationship Builder**: A dedicated UI to define relationships between Subjects (e.g., `Order.customerId` -> `User.id`) with cardinality (1:1, 1:N).
- **Registry Inspector**: A "live" view of the world's population. Instead of just one instance, see a table of all generated subjects (e.g., 6 Users, 4 Orders) and how they link.
- **Population Controls**: Dynamic controls in the sidebar to adjust how many instances of each subject the world generates.

### 2. Advanced Logic & Bindings

The power of `zod4-mock` lies in its pipeline (Matchers -> Heuristics -> Schema).

- **Logic Editor**: An integrated editor (e.g., Monaco or a refined text area) to write:
  - **Subject Derivations**: `.derive({ fullName: (s) => ... })`.
  - **Schema Matchers**: `.withSchema(schema, subject, { email: (s) => s.email })`.
- **Binding Visualization**: A clear UI to see which schema fields are "bound" to subject fields vs. "autogenerated" via heuristics.
- **Custom Key Generators**: A world-level configuration to define custom heuristics (e.g., "any field ending in `_code` should use this specific logic").

### 3. Execution & Experimentation

- **Overrides & Transforms**: A "Sandbox" tab to test `world.generate(schema, { overrides, transform })` without modifying the base schema.
- **PRNG Visualizer**: Visual feedback on how the seed affects different fields and proof of the "per-field seeding" invariant (adding a field doesn't break other fields).
- **Heuristics Explorer**: A searchable browser of all built-in heuristics (e.g., why does `createdAt` default to a Date?).

### 4. Workflow & DX

- **Real-time Validation**: Linting of schemas and logic to prevent runtime errors in the generator.
- **Unified World Code**: A "Full Output" view that shows the entire world setup in one scrollable file, updating live as you edit.
- **State Persistence**: Save/Load via LocalStorage, URL hashes, or JSON file export.

## 🗺️ Feature Roadmap

### Phase 1: Foundational (High Priority)

- [ ] **Relationship Manager**: UI to define `world.withSubject(A).withSubject(B)` with relationships.
- [ ] **Population Controls**: Slider/Input for `SubjectDef.count` in the sidebar.
- [ ] **Registry Explorer Tab**: A new "Registry" tab in the Output pane showing all generated instances in a table.

### Phase 2: Logic & Bindings (Medium Priority)

- [ ] **Scripting Panel**: Sidebar or Modal to edit `.derive()` and Matcher functions in TypeScript.
- [ ] **Enhanced Binding UI**: Drag-and-drop or select-to-map fields between Schema and Subject.
- [ ] **World-wide Generators**: UI to add custom `KeyGenerator` functions.

### Phase 3: Polish & Advanced Tools (Low Priority)

- [ ] **Heuristic Badges**: Subtle indicators in the builder showing WHICH heuristic (built-in or custom) is active for a field.
- [ ] **Data Diffing**: Visual highlights of what changed when the seed or `optionalProbability` is toggled.
- [ ] **Snapshot Preview**: See what a `toMatchSnapshot()` would look like for the current data.

---

## 💡 Technical Considerations

- **Sandboxed Execution**: Since `derive` and `matchers` are arbitrary JS, we might need a safe way to execute them (or just accept it's a dev tool).
- **Svelte 5 Runes**: Leverage `$derived` for the registry state and `$effect` for real-time validation.
- **Monaco Editor**: Consider integrating Monaco for a better coding experience in the logic panels.
