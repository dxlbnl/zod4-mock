## Description

Third implementation card of B94's docs system. Builds the structured API
reference view and the `docs/api-reference.md` parity guard, then rewrites
D5 to point at the new entry point.

> **Design decision (2026-06-06, review checkpoint):** the authoring model is the
> **HYBRID — TSDoc prose → manifest**, NOT a hand-written manifest. The original
> scope below (a hand-curated `manifest.ts` with a hand-typed `signature` string)
> is superseded. Rationale: a hand-typed signature string is a duplicate of the
> real type and can drift; extracting from the source kills that. Docs live next to
> the code (IDE hover) and the existing api-reference prose is **not** preserved
> (rewritten fresh as TSDoc). See `wiki/progress.md` 2026-06-06.

### Scope (hybrid model)

- **TSDoc docstrings on the real public exports** (in `src/` — `src/index.ts` and
  the files it re-exports) are the **prose source of truth**: each public symbol
  gets a `/** … */` with a description, `@example`(s), and curation tags
  (`@group`, ordering, `@see`, `@since` as needed). Authored fresh (current
  api-reference prose not preserved).

- **A build-time extractor** (`scripts/docs-generate.ts` + a helper) reads the
  TSDoc **and the real compiler signatures** (via `ts-morph` or TypeDoc — pick at
  spec time; likely a new dev dependency → flag) and produces a **generated
  manifest** (the data structure the site + markdown render from). The signature
  is **extracted from the types, never hand-typed** → it cannot drift. A thin
  hand-maintained **curation layer** (ordering/grouping, any symbols to include/
  exclude) may sit alongside, keyed by symbol name.

- **`site/src/routes/docs/api/+page.svelte`** — structured view rendered from the
  generated manifest: per-symbol `<SignatureBlock>` cards, right-rail TOC,
  `<ParameterTable>` for parameterised symbols. (B100 primitives.)

- **`scripts/docs-generate.ts`** — emits both the generated manifest (consumed by
  the site) and `docs/api-reference.md` from a template. Idempotent (regenerate
  from scratch; second run = no diff). Run via `tsx`.

- **`pnpm docs:generate`** — root script, runs the generator (writes).
- **`pnpm docs:check`** — runs the generator in `--check` no-write mode; fails if
  on-disk `docs/api-reference.md` (and/or the committed generated manifest) doesn't
  match what the current TSDoc+types produce. Wired into `pnpm validate`.

- **D5 rewrite** (reframed for the hybrid model):
  - `wiki/decisions.md`: append/amend an ADR for D5 explaining the
    TSDoc-as-source-of-truth shift.
  - `wiki/architecture.md` Rules: the **manager** promotes the new D5 rule
    (spec-writer/implementer MUST NOT edit the Rules section). Proposed wording:
    > When a public API changes, the exported symbol's **TSDoc** in `src/` MUST be
    > updated in the same step; the API manifest and `docs/api-reference.md` are
    > regenerated by `pnpm docs:generate` and parity is verified by
    > `pnpm docs:check`. (→ D5)
  - `CLAUDE.md` — sync the doc rule to match.

- **First commit of regenerated artifact**: running `pnpm docs:generate`
  produces the new canonical shape of `docs/api-reference.md` (+ the generated
  manifest); commit that as the new baseline.

## Acceptance

- `/docs/api` renders as a structured per-symbol view from the generated manifest.
- Signatures shown are extracted from the real types (no hand-typed signature
  strings).
- `pnpm docs:generate` is idempotent; running it twice produces no diff.
- `pnpm docs:check` passes in CI and is part of `pnpm validate`.
- Negative test: change a symbol's TSDoc without regenerating; `pnpm docs:check`
  fails with a useful diff.
- D5 rule + ADR + CLAUDE.md doc-rule line updated to the TSDoc-source model.
- `pnpm validate` + `pnpm site:check` green.
