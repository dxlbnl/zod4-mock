# B136: BUG — override array length wins (an array override sets the element count; supersedes "override never resizes")

## Context

Maintainer-reported (follow-up to B134/B135, via `playground.ts`):

> An array override does **not** resize the array — schema length governance wins. Override
> longer than the generated base → extra entries dropped; override shorter → leftover generated
> elements stay. `overrides: { arr: [...] }` should just produce `arr.length` elements as written.

**Maintainer's decision (the contract this spec formalizes — DECIDED, not re-opened):** when
`options.overrides` supplies an **array** for an array-typed target (a nested array **field** or a
standalone array **path**), the result MUST have exactly `override.length` elements. The library
generates `override.length` base elements (per-element seeded, extending B135's explicit index to
`0..override.length-1`), then per-index deep-merges each override slot onto its base element:
**object slot merges** (generated siblings preserved), **primitive slot replaces**, an
**empty/`undefined` hole** leaves that element **fully generated**. Override length **always**
wins — even over an explicit `.length(N)`. Schema length bounds (`.length()` / `.min()` / `.max()`)
and `defaultArrayLength` govern **only the no-override case** (they constrain *generated* data); an
override array MAY exceed or undercut them — **fixtures may override schema bounds**.

This page elaborates the item card
[wiki/backlog/doing/B136-override-array-length-wins.md](../backlog/doing/B136-override-array-length-wins.md).
It revises three shipped contracts and one rule; see **Supersession** below. Reported
conversationally (no GitHub issue).

> In this page, the keywords MUST, MUST NOT, SHOULD, and MAY are used as defined in
> RFC 2119 — they mark genuine requirements, not emphasis.

### Why this exists — the original B134 repro, fixed without a workaround

[B134](B134-nested-array-field-overrides-replace-instead-of-merge.md) fixed the *sibling-dropping*
half of the bug (an array-field override now per-index deep-merges instead of replacing wholesale),
but **B134-R3** deliberately kept "the override never resizes — schema length governs", so a
consumer wanting exactly N elements had to pin `.length(N)`, and the B135 playground had to add a
`defaultArrayLength: [4, 4]` workaround to get four elements. The maintainer has now reversed that
length decision: the override array length is the count. After B136, the canonical repro —

```ts
const Schema = z.object({
  name: z.string(),
  nested: z.object({ age: z.number(), name: z.string(), number: z.number() }).array(),
  //                                                                          ^ bare array — no .length(), no defaultArrayLength
});
world.generate(Schema, {
  overrides: { nested: Array.from({ length: 4 }, (_, number) => ({ number })) },
});
```

— MUST return exactly **4** `nested` elements, each deep-merged onto a generated base, with **no**
`defaultArrayLength` and **no** `.length()` workaround.

### What changes and what is KEPT (precise scope vs. B134/D34)

The **per-index merge semantics are unchanged** (D34): object slot → `deepMerge`, primitive slot →
replace, empty/`undefined` slot → fully generated, `deepMerge` byte-identical (B18). **Only the
length rule changes**: the generated base now has `override.length` elements instead of being
governed by schema bounds. Concretely, the array branch of `applyOverride`
([src/pipeline.ts:239-246](../../src/pipeline.ts#L239)) today maps over the *generated* base
(`base.map(...)`), so a base shorter than the override silently truncates the merge and a base
longer than the override keeps the tail. B136 makes the **base count equal `override.length`** —
generating additional base elements when the override is longer, and not generating a tail when the
override is shorter — then per-index merges as today. The single per-field override-application site
(D34) stays the one place this happens; pipeline rungs stay override-agnostic; there is no
whole-record merge.

### Apply uniformly across all array-override paths (D14 consistency)

The length rule MUST apply to **every** array-override path so the D14 cross-arm consistency invariant
holds with the new rule:

- **nested array field** (`generate(Obj, { overrides: { arr: [...] } })`) — generated by
  `generateZodArray` ([src/generators/schema/collection.ts:56](../../src/generators/schema/collection.ts#L56))
  with the per-field override applied at `applyOverride` ([src/pipeline.ts:216](../../src/pipeline.ts#L216));
- **standalone primary array** (`generate(S.array(), { overrides: [...] })`, B53) —
  `generateArrayPrimary` ([src/world/engine.ts:1677](../../src/world/engine.ts#L1677));
- **standalone derived array** — `generateArrayDerived` ([src/world/engine.ts:1585](../../src/world/engine.ts#L1585));
- **ad-hoc array** — `generateArrayAdHoc` ([src/world/engine.ts:1757](../../src/world/engine.ts#L1757)).

### Composition with shipped Rules and sibling specs

- **D34** (single override site; rungs override-agnostic; no whole-record merge) — **kept; only its
  array-branch length sub-rule changes** (override now resizes the base to `override.length`). The
  single-site invariant, the override-agnostic rungs, and the no-whole-record-merge invariant all
  stand. The Rule line's "the override never resizing — schema length governs (B53-R2/D14)" clause
  MUST be re-worded to "override length governs the element count; schema bounds constrain only the
  no-override case" — the manager promotes that amendment at Done.
- **D14** (all array arms share the trailing pass) — **kept**, and the new length rule is added to
  all three arms uniformly, exactly as D14 requires ("new behaviour added to one arm MUST be added
  to all three"). The D14 ADR/Rule's "no resize" wording is superseded by this item (see below).
- **B135 / D35** (per-element seeding; `store` value-neutral) — **composed with**: the base count is
  now `override.length`, so the explicit per-element index extends to `0..override.length-1`. Each
  of the `override.length` base elements seeds from a distinct per-element index exactly as B135
  pins, so the generated bases remain pairwise distinct and store-neutral (B136-R7). The `store`
  toggle stays value-neutral over the new base count.
- **B18** (`deepMerge` array-as-leaf) — **byte-unchanged**. The per-index slot merge lives in the
  override-application path, never inside `deepMerge`; B136 edits no merge semantics, only the base
  count (B136-R8).
- **B53-R2** (primary array short/long override) and **B134-R3** (nested-field short/long override)
  — both **superseded**: short no longer keeps a schema-generated tail; long no longer drops extras.
  Both now resolve to `override.length` elements.
- **B134-R6** (matcher-backed / primitive-element array, no-resize) — its **length** clause is
  superseded for the override-array case: the result length is now `override.length`. The merge
  semantics (primitive slot replaces, object slot merges) are unchanged. A matcher-produced array
  longer than the override no longer keeps its tail when an override array is supplied; the matcher
  base is generated to `override.length` and merged positionally. (B134-R6 still governs the
  *no-override* case — a matcher array with no override keeps its own length.)
- **D8** (stored == returned) — satisfied by construction on the field path (the merged value is
  what `result[key]` holds, written before store). On the standalone **primary** array path with a
  pre-populated registry, D8 forbids un-generating already-stored records, which pins the one
  carveout (B136-R6 / resolved Q1).
- **D11** (`PIPELINE` canonical ladder) / **D4 / D10** (determinism) / **D1** (no `any`) / **D13**
  (runtime-agnostic) — all preserved; the override is narrowed from `unknown` exactly as today.

### Performance (per `.claude/practices/performance.md`)

The **no-override hot path MUST be unchanged** (B97/B98). The B97 allocation suite + B98 memory suite
in [site/bench/perf.test.ts](../../site/bench/perf.test.ts) gate per-tier time (>25 % FAIL) and memory
(>50 % FAIL) against `site/bench/results/baseline.json`, measuring `simple` / `user` / `nested` /
`matcher` tiers — **none of which pass `overrides`**. The first fast exit of `applyOverride`
(`override === undefined` → `generateRaw()`) and the array arms' no-override length resolution MUST
stay allocation- and PRNG-identical to today. The only behaviour change is on the array-override
path: it already draws element PRNG (B134), and now draws `override.length` element seeds instead of
`schema-length` element seeds — local to the overridden array, which the consumer is overriding
anyway.

## Requirements

### B136-R1: an array-valued field override on a registered object MUST resize the field array to `override.length`, per-index merging onto generated bases

When `world.generate(ObjectSchema, { overrides })` supplies an **array** at an array-typed field
(`overrides[field]`), the system MUST return exactly `overrides[field].length` elements at that
field. It MUST generate `override.length` base elements from the field's element schema and per-index
deep-merge `override[i]` onto base element `i` (object slot merges siblings, primitive slot replaces,
empty/`undefined` slot leaves the element fully generated). Schema length bounds and
`defaultArrayLength` MUST NOT constrain the count when the override is present; they govern only the
no-override case. The override MUST be applied at the single per-field override-application site
(D34); `deepMerge` MUST NOT be modified.

- Scenario: bare array field, no length bound — override yields exactly N elements without a workaround
  GIVEN
  ```ts
  const Schema = z.object({
    name: z.string(),
    nested: z.object({ age: z.number(), name: z.string(), number: z.number() }).array(), // bare: no .length()
  });
  const world = createWorld({ seed: 1 }).withSchema(Schema); // no defaultArrayLength
  ```
  WHEN the consumer calls
  ```ts
  const r = world.generate(Schema, {
    overrides: { nested: Array.from({ length: 4 }, (_, number) => ({ number })) },
  });
  ```
  THEN `r.nested.length === 4` (the override length wins; no `defaultArrayLength`/`​.length()`
  workaround) AND for each `i in {0,1,2,3}`: `r.nested[i].number === i` (override won) AND
  `typeof r.nested[i].age === "number"` AND `typeof r.nested[i].name === "string"` AND
  `r.nested[i].name.length > 0` (generated siblings survive). This is the original B134 repro,
  now resized by the override.

### B136-R2: an override array LONGER than the schema-generated default MUST produce `override.length` elements (extras generate, not dropped)

When the override array is **longer** than the count the schema/`defaultArrayLength` would generate
without an override, the result MUST have `override.length` elements — the extra slots MUST be
**fully-generated base elements** merged with their override slot, NOT dropped.

- Scenario: override of length 5 on a `defaultArrayLength: [2, 2]` field → 5 elements
  GIVEN
  ```ts
  const Schema = z.object({
    items: z.object({ k: z.number(), v: z.string() }).array(),
  });
  const world = createWorld({ seed: 1, defaultArrayLength: [2, 2] }).withSchema(Schema);
  ```
  WHEN the consumer calls
  ```ts
  const r = world.generate(Schema, {
    overrides: { items: [{ k: 10 }, { k: 11 }, { k: 12 }, { k: 13 }, { k: 14 }] },
  });
  ```
  THEN `r.items.length === 5` (the 5-entry override wins over the default of 2 — extras are NOT
  dropped) AND for each `i in {0..4}`: `r.items[i].k === 10 + i` AND `typeof r.items[i].v === "string"`
  with `r.items[i].v.length > 0` (each extra slot generated a base element whose `v` sibling survives
  the merge).

### B136-R3: an override array SHORTER than the schema-generated default MUST produce `override.length` elements (generated tail not kept)

When the override array is **shorter** than the count the schema/`defaultArrayLength` would generate
without an override, the result MUST have exactly `override.length` elements — there MUST be no
schema-generated tail beyond `override.length`.

- Scenario: override of length 1 on a `defaultArrayLength: [4, 4]` field → 1 element
  GIVEN
  ```ts
  const Schema = z.object({
    items: z.object({ k: z.number(), v: z.string() }).array(),
  });
  const world = createWorld({ seed: 1, defaultArrayLength: [4, 4] }).withSchema(Schema);
  ```
  WHEN the consumer calls
  ```ts
  const r = world.generate(Schema, { overrides: { items: [{ k: 100 }] } });
  ```
  THEN `r.items.length === 1` (the single-entry override wins over the default of 4 — the generated
  tail is NOT kept) AND `r.items[0].k === 100` AND `typeof r.items[0].v === "string"` with
  `r.items[0].v.length > 0` (the one element's `v` sibling survives the merge).

### B136-R4: override length MUST win over an explicit `.length(N)` on the field array

When the field array carries an explicit `.length(N)` schema bound, an override array of a different
length MUST still produce `override.length` elements — the override length wins over the explicit
`.length(N)`.

- Scenario: 5 overrides on a `.length(3)` field → 5 elements
  GIVEN
  ```ts
  const Schema = z.object({
    items: z.object({ k: z.number(), v: z.string() }).array().length(3),
  });
  const world = createWorld({ seed: 1 }).withSchema(Schema);
  ```
  WHEN the consumer calls
  ```ts
  const r = world.generate(Schema, {
    overrides: { items: [{ k: 0 }, { k: 1 }, { k: 2 }, { k: 3 }, { k: 4 }] },
  });
  ```
  THEN `r.items.length === 5` (the 5-entry override wins over the schema's `.length(3)`) AND for each
  `i in {0..4}`: `r.items[i].k === i` AND `typeof r.items[i].v === "string"` with
  `r.items[i].v.length > 0`. (Without an override the same field yields exactly 3 elements — the
  `.length(3)` bound governs the no-override case, B136-R9.)

### B136-R5: a sparse hole in the override array MUST yield a fully-generated element at that index

When the override array has a sparse hole or an explicit `undefined` at index `i` (e.g.
`[{ x: 0 }, , { x: 2 }]`), the element at position `i` MUST be a **fully-generated** base element
(no override merged), and the result length MUST still be `override.length`.

- Scenario: sparse hole at the middle index → fully-generated middle element
  GIVEN
  ```ts
  const Schema = z.object({
    items: z.object({ x: z.number(), y: z.string() }).array(),
  });
  const world = createWorld({ seed: 1 }).withSchema(Schema);
  ```
  WHEN the consumer calls
  ```ts
  const r = world.generate(Schema, { overrides: { items: [{ x: 0 }, , { x: 2 }] } }); // hole at index 1
  ```
  THEN `r.items.length === 3` AND `r.items[0].x === 0` AND `r.items[2].x === 2` AND
  `typeof r.items[1].x === "number"` with `r.items[1].x` not constrained by any override (a
  fully-generated element) AND each of `r.items[0].y`, `r.items[1].y`, `r.items[2].y` is a non-empty
  string (every slot, including the hole, has its `y` sibling generated).

### B136-R6: the standalone primary-array path MUST resize to `override.length` for a fresh world, and apply the D8 carveout when records pre-exist

On the standalone primary-array path (`world.generate(RegisteredSchema.array(), { overrides: [...] })`,
B53) the override length MUST govern the element count the same way as the field path. For a **fresh
world** (`existingCount === 0`) the result MUST have exactly `override.length` elements. When the
registry already holds `existingCount > 0` records of the inner schema, D8 forbids un-generating
already-stored records, so the result length MUST be `max(existingCount, override.length)`: the
overrides MUST be applied at positions `0..override.length-1`, the pre-existing stored records at
positions `0..existingCount-1` MUST be returned untouched (per B53-R3's D8 pinning — overrides at
indices `< existingCount` are ignored where a stored record occupies that position), and any positions
`[existingCount, override.length)` MUST be freshly generated and merged with their override slot.

- Scenario: fresh primary array, override of length 5, no `.length` — 5 elements
  GIVEN
  ```ts
  const Person = z.object({ id: z.string(), name: z.string() });
  const world = createWorld({ seed: 1 }).withSchema(Person);
  ```
  WHEN the consumer calls
  ```ts
  const result = world.generate(Person.array(), {
    overrides: [{ name: "a" }, { name: "b" }, { name: "c" }, { name: "d" }, { name: "e" }],
  });
  ```
  THEN `result.length === 5` (override length wins — no schema bound was supplied) AND
  `result.map((p) => p.name)` deep-equals `["a", "b", "c", "d", "e"]` AND each `result[i].id` is a
  non-empty string (sibling preserved) AND `world.registry.all(Person)` deep-equals `result` (D8 —
  stored == returned).

- Scenario: pre-populated registry — length is `max(existingCount, override.length)`, head untouched
  GIVEN
  ```ts
  const Person = z.object({ id: z.string(), name: z.string() });
  const world = createWorld({ seed: 1 }).withSchema(Person);
  world.populate(Person, 3); // three pre-existing stored records
  const head = world.registry.all(Person).slice(0, 3).map((p) => p.name);
  ```
  WHEN the consumer calls
  ```ts
  const result = world.generate(Person.array(), {
    overrides: [{ name: "x" }, { name: "y" }, { name: "z" }, { name: "w" }, { name: "v" }],
  });
  ```
  THEN `result.length === 5` (`max(existingCount=3, override.length=5)`) AND
  `result.slice(0, 3).map((p) => p.name)` deep-equals `head` (the three pre-existing stored records
  are returned untouched — D8; override slots 0–2 ignored at those positions) AND
  `result.slice(3).map((p) => p.name)` deep-equals `["w", "v"]` (positions 3–4 are freshly generated
  and carry their override slot) AND `world.registry.all(Person)` deep-equals `result` (D8 —
  stored == returned).

### B136-R7: the `override.length` base elements MUST be per-element-distinct and store-neutral (composes with B135)

The `override.length` base elements MUST seed from distinct per-element indices `0..override.length-1`
(extending B135's explicit per-element index to the new base count) so the generated (non-override)
fields of the base elements are pairwise distinct, and MUST be identical under `store: true` and
`store: false` at each position (B135/D35 — `store` value-neutral). Distinctness MUST hold across the
**new** slots produced when the override is longer than the schema default (B136-R2), and over a
fully-generated hole (B136-R5).

- Scenario: longer override → generated bases of the extra slots are pairwise distinct, store-neutral
  GIVEN
  ```ts
  const Schema = z.object({
    items: z.object({ k: z.number(), v: z.string() }).array(),
  });
  const worldOn = createWorld({ seed: 7, defaultArrayLength: [1, 1] }).withSchema(Schema);
  const worldOff = createWorld({ seed: 7, defaultArrayLength: [1, 1] }).withSchema(Schema);
  ```
  WHEN
  ```ts
  const overrides = { items: [{ k: 0 }, { k: 1 }, { k: 2 }, { k: 3 }] }; // length 4, default would be 1
  const on = worldOn.generate(Schema, { overrides });
  const off = worldOff.generate(Schema, { store: false, overrides });
  ```
  THEN `on.items.length === 4` AND `new Set(on.items.map((it) => it.v)).size === 4` (the four
  generated `v` siblings — including the three slots beyond the default-1 base — are pairwise distinct)
  AND `JSON.stringify(off.items) === JSON.stringify(on.items)` (store-off elements are element-wise
  byte-equal to store-on at every position — D35 value-neutral over the override-driven base count).

### B136-R8: `deepMerge` MUST NOT be modified (B18 array-as-leaf preserved)

`deepMerge` in [src/utils/merge.ts](../../src/utils/merge.ts) MUST remain byte-identical: it MUST
continue to treat any array `source` as a leaf that replaces the target verbatim (B18). The
override-length-driven base count and the per-index slot merge MUST live in the override-application
path / array arms, never inside `deepMerge`. No edit to `src/utils/merge.ts` is permitted by this item.

- Scenario: `deepMerge` array-as-leaf semantics are intact
  GIVEN B136 is implemented
  WHEN `src/utils/merge.ts` is read and `deepMerge({ tags: ["a", "b", "c"] }, { tags: ["x", "y"] })`
  is evaluated
  THEN `src/utils/merge.ts` carries no B136-introduced change to `deepMerge` (the `isPlainObject`
  guard and array-replace early return are byte-identical to pre-B136) AND the call returns
  `{ tags: ["x", "y"] }` (array replaces wholesale, B18 preserved).

### B136-R9: the no-override case MUST stay governed by schema bounds / `defaultArrayLength`, and the no-override hot path MUST stay performance-neutral (B97/B98 green)

When no array override is present, the element count MUST stay governed by the schema bounds
(`.length()` / `.min()` / `.max()`) else `defaultArrayLength` — B136 MUST NOT change the no-override
length resolution. The B97 allocation suite and B98 memory suite in
[site/bench/perf.test.ts](../../site/bench/perf.test.ts) MUST stay within their baseline guardrails
(no FAIL) after the change; the `override === undefined` field path MUST remain the first fast exit
with no added allocation and no extra PRNG draw.

- Scenario: no override → schema length governs, B97/B98 green
  GIVEN
  ```ts
  const Schema = z.object({ items: z.object({ k: z.number() }).array().length(3) });
  const world = createWorld({ seed: 1 }).withSchema(Schema);
  ```
  WHEN the consumer calls `const r = world.generate(Schema);` (no overrides) AND `pnpm test` runs the
  `site/bench/perf.test.ts` B97/B98 regression gate
  THEN `r.items.length === 3` (the `.length(3)` bound governs the no-override case — unchanged) AND
  the perf suite exits with no per-tier time FAIL (>25 %) and no memory FAIL (>50 %) on the
  `simple` / `user` / `nested` / `matcher` tiers (none of which pass `overrides`), confirming the
  no-override hot path is allocation- and PRNG-neutral.

### B136-R10: regression test — the playground repro yields exactly N elements without a `defaultArrayLength` workaround

A regression test MUST be added under `tests/unit/` (D6) reproducing the maintainer's case: a
registered object with a **bare** nested object-array field (no `.length()`, no `defaultArrayLength`),
overridden with an N-entry partial-object array, MUST return exactly N elements, each with its
un-overridden siblings preserved. If a regression re-introduces schema-length governance over the
override, this test MUST be the one that fails.

- Scenario: card repro — bare array field + 4-entry override → 4 elements, siblings kept
  GIVEN


  every `i in {0,1,2,3}`: `Object.keys(r.nested[i]).sort()` deep-equals `["age", "name", "number"]`
  AND `typeof r.nested[i].age === "number"` AND `typeof r.nested[i].name === "string"` with

## Out of scope

- **The no-override length rule.** Unchanged — schema bounds (`.length()` / `.min()` / `.max()`) and
  `defaultArrayLength` still govern the count when no override array is present (B136-R9). B136 only
  changes the count when an override **array** is supplied for the target.
- **Object-field (`deepMerge`) override semantics.** Unchanged — a plain-object override still
  deep-merges (B12/B18/D34). B136 changes only the array case's length.
- **Per-index merge semantics.** Unchanged — object slot merges, primitive slot replaces, empty slot
  generates (D34). Only the base count changes.
- **Mutating registry storage for pre-existing records on the primary path.** Out of scope — the D8
  carveout (B136-R6) returns pre-existing stored records untouched; overriding records already in the
  registry would need a deliberate D8 revisit (rejected at B53 and not re-opened here).
- **Changing `deepMerge`** (B18) — explicitly forbidden by B136-R8.
- **Multi-level array-of-array overrides** (`z.array(z.array(...))` with array-of-array override
  entries) — still out of scope as in B134; the override slot maps positionally to one array level,
  and each element's own resolution handles nesting within it.
- **A separate matcher-backed-array length item.** B134-R6's matcher-base length now defers to the
  override length when an override array is present; the no-override matcher case is unchanged. No new
  matcher item is needed.
