# B135: BUG — `store: false` array of a registered schema yields identical elements (per-element index collapses to 0)

## Context

User-reported (via `playground.ts`, the "failing overrides" case): generating an array
of a **registered primary** schema under `store: false` returns N **identical** records
instead of N distinct ones. With `nestedThing` registered and a field
`nested: nestedThing.array()`:

```ts
const nestedThing = z.object({ age: z.number(), name: z.string(), number: z.number() });
const schema = z.object({ name: z.string(), nested: nestedThing.array() });
const world = createWorld().withSchema(nestedThing).withSchema(schema);

world.generate(schema, { defaultArrayLength: [4, 4], store: false,
  overrides: { nested: Array.from({ length: 4 }, (_, number) => ({ number })) } });
```

Every `nested` element comes back as the **same** record (`{ age: 46, name: "Grace
Johnson", number: i }`), differing only in the override-injected `number`. The repro is
**independent of overrides** — `store: false` alone collapses the elements; B134's
single-override-application flow only *exposed* it (pre-B134 an array override
short-circuited at pipeline step 0 and never generated the base array, hiding the
identical-base-elements defect for the override case).

### Root cause (confirmed)

In `generateArrayPrimary`'s **store-off** branch
([src/world/engine.ts:1676-1683](../../src/world/engine.ts#L1676)) each element is produced
by `generateAndStorePrimary(innerSchema, primaryReg, …)` inside a synchronous `Array.from`
loop. `generateAndStorePrimary` derives the per-record seed from
`recordIndex = registry.count(schema) + pending`
([src/world/engine.ts:1277-1278](../../src/world/engine.ts#L1277)): it increments `pending`
at entry and **decrements it in `finally`**
([src/world/engine.ts:1307-1308](../../src/world/engine.ts#L1307)). The `pending` counter
exists for **re-entrant** generation (a record whose generation triggers another record of
the same schema), not for **sequential array siblings**: across the `Array.from` loop each
sibling enters at `pending == 0` (the previous sibling already decremented in `finally`),
and under `store: false` the `registry.store` call is suppressed
([src/world/engine.ts:1300-1302](../../src/world/engine.ts#L1300)) so `registry.count` never
advances. Every element therefore computes
`recordIndex = count(0) + pending(0) = existingCount` → identical `recordId`
(`reg<id>#<existingCount>`) → identical field seed → identical record.

The store-**on** `while` loop ([src/world/engine.ts:1685-1690](../../src/world/engine.ts#L1685))
reads `i = registry.count(innerSchema)` and the store write advances that count per element,
so its records get distinct indices `existingCount..existingCount+N-1` — distinct seeds,
distinct records. **That asymmetry is the bug**: the store-off path lost the per-element
index. Toggling `store` MUST be value-neutral (D4/D10), so the store-off path must seed each
element from the same per-record index the store-on path uses.

### Fix shape

Thread the per-element index **explicitly** into `generateAndStorePrimary` for the store-off
branch — the i-th element seeds from `recordIndex = existingCount + i`, identical to the
store-on path's record at the same position — rather than relying on the
`registry.count + pending` derivation that self-cancels under `store: false`. The store-on
path stays byte-identical (it already derives distinct indices from `registry.count`). The
B53 per-index override threading (`overrides: overridesArr?.[i]`) in the store-off branch is
preserved unchanged — the fix only fixes the seed index, not the override slot.

This item is scoped to the **primary** store-off arm (the reported, confirmed defect) plus
the structurally-identical **derived auto-provision-under-`store: false`** collapse (B135-R4
below — same `registry.count`-frozen pattern; see Scope). The common derived store-off path
(sources already in the registry) is **not** affected — `collectSourcePairs` yields distinct
`sourceIndex` 0..N-1 there (see Out of scope).

**Second collapse site (the nested registered-array FIELD case, B135-R3).** A nested
registered-schema array *field* (`Schema.nested = NestedThing.array()`) does **not** route
through `generateArrayPrimary` — it is generated by `generateZodArray`
(`src/generators/schema/collection.ts`) via a per-element `ctx.generate(element)`, which
resolves to `generatePrimary` → `generateAndStorePrimary` and had the **identical**
`registry.count + pending` collapse. The fix threads the explicit per-element index here too,
via an `@internal recordIndex?: number` field on `GenerateOptions` — the sanctioned alternative
threading shape, since `ctx.generate` accepts only `GenerateOptions` and cannot take a private
parameter — forwarded by `generatePrimary` into `generateAndStorePrimary`. This is D29-compliant
(`@internal`, no user call path) and non-breaking. So R3's repro is fixed at this second site,
while R1/R2 (the top-level `generate(S.array())` call) are fixed at `generateArrayPrimary`'s
store-off branch.

### Composition with binding Rules

- **D1** — no `any`; the threaded index is a `number`. If it travels as a field on
  `GenerateOptions<unknown>` it MUST be `@internal` per D29 (and is non-breaking — purely
  engine-internal plumbing with no user call path). The preferred shape is a **private
  parameter** on `generateAndStorePrimary` (no public-type change at all); either is
  acceptable provided D29 is honoured if the option route is taken.
- **D4 / D10** — the fix makes the store-off element seeds **equal** the store-on seeds at
  the same positions, restoring "toggling `store` MUST NOT change the i-th element's values".
  No new PRNG draws are introduced on the store-on path; the store-off path's per-record
  `recordPrng` is seeded from the corrected `recordId` (`reg<id>#<existingCount+i>`).
- **D6** — a regression test pins the reported collapse (B135-R3).
- **D8** — vacuous under `store: false` (nothing is stored); the store-on path is unchanged,
  so "stored == returned" holds there as before (B135-R5).
- **D11** — `PIPELINE` is untouched; the fix is the `recordIndex` seed derivation upstream of
  the per-field ladder.
- **D14 / D34** — the B53 per-index override threading and the single per-field
  override-application site are preserved unchanged; the fix only corrects the seed index.

## Requirements

### B135-R1: store-off registered-primary array elements MUST seed from distinct per-element indices

`WorldImpl.generateArrayPrimary`'s store-off branch
([src/world/engine.ts:1676-1683](../../src/world/engine.ts#L1676)) MUST produce the i-th
returned element with the per-record seed `recordId = reg<effectiveRegId>#<existingCount + i>`
(the same `recordId` the store-on `while` loop produces for the record it writes at that
position), so the N returned records are pairwise distinct in their generated (non-override)
fields. The seed MUST be derived from an **explicit** per-element index, NOT from
`registry.count(schema) + pending` (which self-cancels under `store: false` and collapses
every element to the same index).

- Scenario: four store-off elements of a registered schema are pairwise distinct
  GIVEN
  ```ts
  const NestedThing = z.object({ age: z.number(), name: z.string(), number: z.number() });
  const world = createWorld({ seed: 1 }).withSchema(NestedThing);
  ```
  WHEN the consumer calls
  `const result = world.generate(NestedThing.array().length(4), { store: false });`
  THEN `result.length === 4` AND the four records are pairwise distinct — i.e.
  `new Set(result.map((r) => JSON.stringify(r))).size === 4` (no two elements are
  byte-identical).

### B135-R2: toggling `store` MUST NOT change the i-th store-off element's values

For a registered primary inner schema on a fresh world, the records returned by
`world.generate(S.array().length(N), { store: false })` MUST be element-wise equal to the
records the store-on call `world.generate(S.array().length(N))` returns at the same positions
(same seed, same registration, same call). Only the registry side effect differs (D4/D10 —
the store toggle is value-neutral; B10-R7 extended to the registered-primary array arm).

- Scenario: store-off elements equal the store-on first-N records position-by-position
  GIVEN two independent worlds with the same seed and registration:
  ```ts
  const NestedThing = z.object({ age: z.number(), name: z.string(), number: z.number() });
  const worldOn = createWorld({ seed: 7 }).withSchema(NestedThing);
  const worldOff = createWorld({ seed: 7 }).withSchema(NestedThing);
  ```
  WHEN
  ```ts
  const on = worldOn.generate(NestedThing.array().length(4)); // store on
  const off = worldOff.generate(NestedThing.array().length(4), { store: false }); // store off
  ```
  THEN `JSON.stringify(off) === JSON.stringify(on)` (element-wise byte-equal at every
  position) AND `worldOff.registry.count(NestedThing) === 0` (store-off wrote nothing) AND
  `worldOn.registry.count(NestedThing) === 4` (store-on wrote all four — D8).

### B135-R3: regression — the playground `store: false` registered-array repro MUST produce distinct elements

The reduced playground repro (a registered schema, `store: false`, an array of that schema)
MUST return per-element-distinct records. This requirement pins the user-reported defect (D6).

- Scenario: nested registered-schema array field under `store: false` is distinct, overrides preserved
  GIVEN
  ```ts
  const NestedThing = z.object({ age: z.number(), name: z.string(), number: z.number() });
  const Schema = z.object({ name: z.string(), nested: NestedThing.array() });
  const world = createWorld({ seed: 1 }).withSchema(NestedThing).withSchema(Schema);
  ```
  WHEN the consumer calls
  ```ts
  const result = world.generate(Schema, {
    defaultArrayLength: [4, 4],
    store: false,
    overrides: { nested: Array.from({ length: 4 }, (_, number) => ({ number })) },
  });
  ```
  THEN `result.nested.length === 4` AND `result.nested.map((n) => n.number)` deep-equals
  `[0, 1, 2, 3]` (the per-index override still lands — B53 threading intact) AND the four
  elements are pairwise distinct in their **generated** fields, observed as
  `new Set(result.nested.map((n) => `${n.age}|${n.name}`)).size > 1` (the `age`/`name` pairs
  are no longer all identical — the collapse is fixed).

### B135-R4: store-off derived array elements auto-provisioned under `store: false` MUST seed from distinct indices

When a derived array is generated under `store: false` AND its sources must be
**auto-provisioned** (the `from:` source registry is empty, so
`generateArrayDerived`'s floor loop at [src/world/engine.ts:1580-1588](../../src/world/engine.ts#L1580)
creates them), the auto-provisioned source records — and hence the derived records keyed on
their `sourceIndex` (`dreg<schemaId>#<sourceIndex>`) — MUST carry **distinct** `sourceIndex`
values `0..N-1`. They MUST NOT all collapse to the same index because
`registry.count(fromSchema)` is frozen under suppressed writes (the structural twin of
B135-R1). When the source registry is already populated, `collectSourcePairs` already yields
distinct `sourceIndex` and this requirement is satisfied with no change.

- Scenario: derived array auto-provisioned under `store: false` yields distinct elements
  GIVEN
  ```ts
  const Source = z.object({ id: z.uuid(), label: z.string() });
  const Derived = z.object({ sourceId: z.uuid(), tag: z.string() });
  const world = createWorld({ seed: 1 })
    .withSchema(Source)
    .withSchema(Derived, { from: Source, matchers: { sourceId: (ctx) => ctx.source.id } });
  // Source registry intentionally empty → the derived array must auto-provision sources.
  ```
  WHEN the consumer calls
  `const result = world.generate(Derived.array().length(3), { store: false });`
  THEN `result.length === 3` AND the three records are pairwise distinct —
  `new Set(result.map((r) => JSON.stringify(r))).size === 3` — AND
  `world.registry.count(Derived) === 0` AND `world.registry.count(Source) === 0` (B10-R2/R4:
  no derived or auto-provisioned-source write under `store: false`).

### B135-R5: the store-on primary array path MUST stay byte-identical

`WorldImpl.generateArrayPrimary`'s store-on `while`-loop path
([src/world/engine.ts:1685-1696](../../src/world/engine.ts#L1685)) MUST remain
byte-equivalent to the pre-B135 implementation for the same seed and registration: same
records, same field values, same ordering, same registry writes. The fix MUST change only how
the **store-off** branch derives each element's seed index; the store-on branch's
`i = registry.count(innerSchema)` derivation MUST be untouched.

- Scenario: store-on array call is unchanged by the fix
  GIVEN
  ```ts
  const NestedThing = z.object({ age: z.number(), name: z.string(), number: z.number() });
  const world = createWorld({ seed: 3 }).withSchema(NestedThing);
  ```
  WHEN the consumer calls `const result = world.generate(NestedThing.array().length(4));`
  (no `store` option — default store on)
  THEN `result.length === 4`, `world.registry.count(NestedThing) === 4`,
  `world.registry.all(NestedThing)` deep-equals `result` (D8 — stored == returned), AND the
  records are pairwise distinct (this was already correct pre-B135 and MUST stay so).

### B135-R6: changeset entry — patch bump

A changeset file at `.changeset/b135-store-false-registered-array-identical-elements.md` MUST
be added in the same step, declaring a **patch** bump for `zod4-mock`. Rationale: this is a
determinism/correctness fix with **no public API surface change** (no new method, no new
user-facing option, no signature change) — `store: false` array output that was collapsing is
corrected to match the store-on output. The changeset body MUST summarise the bug (store-off
registered-schema array elements collapsed to identical records because each seeded from a
self-cancelling `registry.count + pending` index) and the fix (thread an explicit per-element
index so the i-th store-off element matches the store-on record at index i). No `(closes #N)`
line — reported conversationally via the playground.

- Scenario: changeset exists with the right bump and content
  GIVEN the B135 change applied
  WHEN `.changeset/b135-store-false-registered-array-identical-elements.md` is read
  THEN its frontmatter contains `"zod4-mock": patch` AND its body summarises the collapse and
  the explicit-per-element-index fix.

## Out of scope

- **The common derived store-off path with pre-populated sources.** When the `from:` source
  registry already holds records, `generateArrayDerived` builds its pairs via
  `collectSourcePairs` ([src/world/engine.ts:1784-1785](../../src/world/engine.ts#L1784)),
  which assigns each pair a distinct `sourceIndex` (`0..sources.length-1`) read from the
  registry contents — independent of `effectiveStore`. Those derived records already seed from
  distinct `dreg<schemaId>#<sourceIndex>` keys and are **not** affected by this bug. Only the
  **auto-provision-under-`store: false`** sub-case (B135-R4) shares the collapse, and it is the
  only derived case in scope.
- **The store-on path's seed derivation.** Unchanged (B135-R5). The store-on `while` loop
  already derives distinct `i` from `registry.count`; the fix touches only the store-off
  branch.
- **The B53 per-index override threading.** Preserved verbatim — the fix corrects the seed
  index, not the `overrides: overridesArr?.[i]` slot. B135 does not relitigate B53 / D34.
- **Caller-side `.min/.max/.length` and per-index override semantics.** Already pinned by
  B43/B52/B53; B135 does not change array length resolution or override merge semantics — only
  the per-element seed index under `store: false`.
- **The ad-hoc (unregistered) array path.** It already forks a distinct per-element PRNG
  (`genPrng.fork("[i]")`, [src/world/engine.ts:1705-1709](../../src/world/engine.ts#L1705)),
  so its store-off elements are already distinct. Untouched.
- **Re-entrant generation's `pending` counter.** The `pending` mechanism stays for its real
  purpose (a record whose generation triggers another record of the same schema). B135 does not
  remove or repurpose it; it adds an explicit index for the sequential-sibling case the
  `pending` counter was never designed to cover.
- **Changing the rolled `target` / `existingCount` floor under `store: false`.** Unchanged
  (B44 governs the length). B135 only fixes which seed each of those N elements uses.

## Open questions

All three questions raised on the item card are resolved below — **0 blocking, 3 non-blocking**.
The card carries `flags: [review]` because the fix touches the determinism contract + seed
derivation; that is a manager/review-checkpoint matter, not a blocking spec question.

- **Q1 — Thread the per-element index explicitly into `generateAndStorePrimary` (vs. relying
  on `registry.count + pending`)? — Resolved, non-blocking.** Adopted: the store-off branch
  passes an explicit `recordIndex = existingCount + i` so the seed is
  `reg<id>#<existingCount+i>`, matching the store-on path exactly. This is the minimal correct
  fix and makes store-on/store-off determinism identical (B135-R1/R2). Threading shape: the
  final implementation used **both** sanctioned shapes — the **private parameter** on
  `generateAndStorePrimary` for the top-level `generateArrayPrimary` / derived store-off paths
  (no public-type change), AND the **`@internal recordIndex?: number` field on `GenerateOptions`**
  (D29) for the nested registered-array FIELD path through `generateZodArray` → `ctx.generate`
  → `generatePrimary`, where `ctx.generate` accepts only `GenerateOptions` and cannot take a
  private parameter. Both are D29-compliant and non-breaking. Recorded; not blocking.

- **Q2 — Does the same collapse affect the derived store-off array path, or only primary? —
  Resolved by code inspection, non-blocking.** Determined from the engine: the derived arm
  collapses **only** in the auto-provision-under-`store: false` sub-case (the
  `registry.count(fromSchema)`-frozen floor loop), which is the structural twin of the primary
  collapse and is therefore **in scope** (B135-R4). The common derived path (pre-populated
  sources) assigns distinct `sourceIndex` via `collectSourcePairs` and is **not** affected
  (Out of scope). Smallest correct scope = primary (R1-R3) + derived auto-provision (R4).
  Recorded; not blocking.

- **Q3 — Existing-count base when the registry already holds records of the inner schema from
  an earlier store-on call. — Resolved, non-blocking.** Under `store: false` the store write is
  suppressed, so the concern is only the **starting index**, not a registry mutation. The
  correct base is `existingCount = registry.count(innerSchema)` captured at the top of
  `generateArrayPrimary` ([src/world/engine.ts:1652](../../src/world/engine.ts#L1652)): the
  store-off elements seed from `existingCount + i`, mirroring the store-on `while` loop, which
  starts its `i` at the same `existingCount`. This keeps store-off and store-on element-wise
  equal even when prior records exist (B135-R2's invariant holds for any `existingCount`).
  Recorded; not blocking.

No blocking open questions remain; the spec can advance to `test-writer`.
