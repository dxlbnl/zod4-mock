# B115: Group the /docs/api reference by category

## Context

The `/docs/api` route currently renders the entire public API surface as **one flat
list** — a single `{#each API_MANIFEST}` of per-symbol `<h2>` blocks inside a `<DocPage>`,
with a flat right-rail TOC ("On this page") derived from those `<h2>`s. A reader landing on
the page gets ~35 symbols with no mental model: `generate` sits in the same undifferentiated
list as `TraceResolution`. The maintainer site review (2026-06-07) flagged this as the
headline gap. See the item card:
[wiki/backlog/doing/B115-docs-api-grouped-by-category.md](../backlog/doing/B115-docs-api-grouped-by-category.md).

This builds directly on **B102**
([wiki/specs/B102-docs-structured-api-parity-guard.md](B102-docs-structured-api-parity-guard.md)),
which established the HYBRID docs pipeline: TSDoc on `src/` exports → a build-time `ts-morph`
extractor (`scripts/docs/extract.ts`) + a hand-maintained curation layer
(`scripts/docs/curation.ts`) → a **generated** manifest with two render targets
(`site/src/lib/docs/api/manifest.generated.ts` for the site view and `docs/api-reference.md`
via `scripts/docs-generate.ts`), guarded by `pnpm docs:check` inside `pnpm validate`. B85
added the "World Explorer" trace symbols and a `World Explorer` curation group.

**Ground truth (already in place):** the curation layer **already carries a `group` per
symbol** (`CurationEntry.group`), the extractor already threads `group` through onto each
`ManifestSymbol`, and the generated site manifest (`ApiSymbol`) already has a `group` field
populated per entry. So this card does **not** need to add the group field — the data exists.
What is missing is **rendering** it: the site view ignores `group` and renders flat, the TOC
is flat, and `docs/api-reference.md` is a flat per-symbol list. B115 is mostly a **render +
taxonomy** task: surface the existing groups as grouped sections + a grouped TOC in the site
view, mirror the grouping in `docs/api-reference.md`, and curate the final group taxonomy so
it reads as a clear mental model.

This card complies with the standing **Rules** in
[wiki/architecture.md](../architecture.md):

- **D5 / D24** — `site/src/lib/docs/api/manifest.generated.ts` and `docs/api-reference.md`
  are **generated artifacts** and **MUST NOT** be hand-edited. The group taxonomy is curated
  by editing `scripts/docs/curation.ts` (the only hand-maintained input besides the `src/`
  TSDoc); both targets are then regenerated by `pnpm docs:generate` and kept in sync by
  `pnpm docs:check` (part of `pnpm validate`). The extractor MUST stay `ts-morph`-based.
- **D21** — any new CSS lives in `@layer site` in `site/src/lib/styles/app.css` or
  scoped component styles; no new layer.
- **D1** — no `any` anywhere this card touches; new relative imports use `.js` extensions.

> In this page, the keywords MUST, MUST NOT, SHOULD, and MAY are used as defined in
> RFC 2119 — they mark genuine requirements, not emphasis.

### Proposed group taxonomy (curated; non-blocking — refinable at the designer/review pass)

The card names "World methods / matchers / types / Explorer" as the mental model. The
existing `CURATION` already has fine-grained groups (`Entry points`, `PRNG`, `Generators`,
`Localization`, `Core types`, `Generation types`, `Schema registration`,
`Override / transform`, `Explain`, `World Explorer`, `Localization types`). That is _more_
granularity than a reader needs and reads as a long list of small buckets. B115 consolidates
to a **concrete, evaluator-orientable set of groups**, in this render order:

1. **Getting started** — the zero-config + world entry points: `generate`, `createWorld`.
2. **World & registry** — the session + store types a consumer reads: `World`,
   `WorldOptions`, `Registry`.
3. **Matchers & generation context** — what a matcher/generator author touches:
   `GeneratorContext`, `MatcherCtx`, `BoundGenerators`, `SchemaOpts`, `SchemaKeyMap`,
   `KeyGenerator`, `KeyPattern`.
4. **Generators & key heuristics** — the built-in generator surface: `generators`, `data`,
   `generateFromSchema`, `generateFromKey`, `DEFAULT_KEY_MAP`, `DEFAULT_KEY_PATTERNS`.
5. **Options, overrides & explain** — per-call tuning + introspection: `GenerateOptions`,
   `DeepPartial`, `ExplainResult`, `FieldExplanation`, `RelationExplanation`.
6. **Randomness** — the PRNG surface: `createPrng`, `fieldSeed`, `Prng`, `PrngGen`.
7. **World Explorer (trace)** — the provenance contract: `WorldTrace`, `TraceNode`,
   `TraceField`, `TraceEdge`, `TraceResolution`.
8. **Localization** — locales + locale data: `extend`, `LocaleData`, `LastNamePrefix`,
   `Currency`.

This is a **recommendation curated into `scripts/docs/curation.ts`**, stated here so a
reviewer/designer can adjust group _names_, _order_, or _per-symbol assignment_ at the review
pass without reshaping any requirement below — the requirements are written against "the
groups defined by the curation layer", not against these literal eight names. The hard
contract is: a small set of clearly-labelled groups, each non-empty, every public symbol in
exactly one group, in a sensible reading order. (See Open question 1.)

## Requirements

### B115-R1: Each manifest symbol carries a non-empty curated group

Every symbol in the generated API manifest (both `ApiSymbol` in
`site/src/lib/docs/api/manifest.generated.ts` and the in-memory `ManifestSymbol` the
extractor produces) **MUST** carry a non-empty `group` string drawn from the curation layer,
and every public export of `src/index.ts` **MUST** be assigned to exactly one curated group
(no symbol left with an empty group, no symbol falling through to the default `"Other"`
bucket).

- Scenario: every symbol has a curated group
  - GIVEN the regenerated manifest after `pnpm docs:generate`
  - WHEN a test reads `API_MANIFEST` (or the extractor's `buildManifest()` output)
  - THEN every entry's `group` is a non-empty string, no entry's `group` is `"Other"`, and
    the set of distinct `group` values equals the set of group labels declared in
    `scripts/docs/curation.ts`.
- Scenario: a public export absent from curation is flagged, not silently grouped
  - GIVEN a public export of `src/index.ts` exists with no entry in `CURATION`
  - WHEN the manifest is built / a coverage check runs
  - THEN that symbol is surfaced as un-curated (the B102-R3 default-position/coverage
    behaviour) — it does not silently acquire a real group label.

### B115-R2: The /docs/api site view renders symbols under group section headings

The `site/src/routes/docs/api/+page.svelte` view **MUST** render the manifest as **grouped
sections** rather than a flat list: each curated group renders a section with a visible group
heading (group label), and every symbol belonging to that group renders beneath its group's
heading; groups render in curation order and symbols render in curation order within their
group.

- Scenario: symbols render under their group heading
  - GIVEN `/docs/api` renders against the regenerated grouped manifest
  - WHEN a component/Playwright test queries the page
  - THEN the page contains a visible heading for each curated group label (e.g. a heading
    with text matching the "Getting started" group), and the `generate` symbol's block
    appears in the DOM after that group's heading and before the next group's heading.
- Scenario: group order follows curation order
  - GIVEN the curation layer orders group A before group B
  - WHEN `/docs/api` renders
  - THEN group A's heading appears before group B's heading in document order.

### B115-R3: Each symbol keeps its own stable `#<name>` anchor under the grouped layout

Under the grouped layout, every symbol **MUST** still expose its own in-page anchor whose id
is the symbol `name` (the `#generate`, `#Currency`, … targets B102's deep links and the
B102-R4 TOC contract depend on), so existing per-symbol links do not break when sections are
introduced.

- Scenario: per-symbol anchor survives grouping
  - GIVEN `/docs/api` renders grouped
  - WHEN a test inspects the `generate` symbol's block
  - THEN an element with `id="generate"` exists in the page and navigating to
    `/docs/api#generate` scrolls that symbol's block into view (the symbol heading carries
    `scroll-margin-top` as today).

### B115-R4: The right-rail "On this page" TOC reflects the grouping

The right-rail "On this page" TOC **MUST** reflect the grouping: its entries **MUST** be
organised by group (a group label heading or labelled cluster, with the per-symbol links
nested under their group) rather than presented as one undifferentiated flat list, while every
per-symbol link still targets that symbol's `#<name>` anchor.

- Scenario: TOC is grouped and still links each symbol
  - GIVEN `/docs/api` renders grouped in a real browser (Playwright)
  - WHEN the "On this page" complementary region is queried
  - THEN it shows the group labels as TOC group headings/clusters, AND it still contains a
    navigable link whose `href` is `#generate` (the existing B102-R4 assertion holds) — the
    grouping is additive structure over the same per-symbol links, not a replacement that
    drops them.

### B115-R5: `docs/api-reference.md` is generated with the same grouping

`scripts/docs-generate.ts` **MUST** emit `docs/api-reference.md` with the grouping reflected
— group heading sections containing their symbols, in the same group + within-group order as
the site view — and the file **MUST** remain a generated artifact regenerated by
`pnpm docs:generate` (never hand-edited, D5/D24), with the parity guard still able to localise
drift to a changed symbol.

- Scenario: the markdown groups its symbols
  - GIVEN `pnpm docs:generate` has run
  - WHEN `docs/api-reference.md` is read
  - THEN it contains a heading for each curated group label, every symbol's section appears
    under its group's heading in curation order, and the "Exports overview" still lists every
    manifest symbol exactly once (no symbol dropped or duplicated by the grouping).
- Scenario: drift in one symbol is still localised by docs:check
  - GIVEN an in-sync generated tree, and a single symbol's TSDoc description is edited without
    regenerating
  - WHEN `pnpm docs:check` runs
  - THEN it exits non-zero and its output names the drifted symbol (the B102-R9 diff stays
    symbol-localised; grouping the file MUST NOT collapse the diff to a whole-file mismatch).

### B115-R6: `pnpm docs:generate` stays idempotent and `pnpm validate` stays green

After B115, `pnpm docs:generate` **MUST** remain idempotent (a second run with no
TSDoc/type/curation change produces byte-identical generated files) and `pnpm validate`
(including `docs:check`) **MUST** pass green.

- Scenario: regenerate is a no-op and validate passes
  - GIVEN the grouped generated tree is committed
  - WHEN `pnpm docs:generate` runs a second time and then `pnpm validate` runs
  - THEN the generated files are byte-identical to the committed versions and `pnpm validate`
    completes green with `docs:check` exiting 0.

### B115-R7: No regression to the B102 / B114 `/docs/api` guards

The grouped layout **MUST NOT** regress the existing `/docs/api` guarantees: the B102
`docs-api.spec.ts` TOC-overlap guard (no content block overlaps/clips the TOC at 1440;
parameterised symbols render a `<ParameterTable>`, type-only symbols render none) and the
B114 responsive behaviour (mobile single-column, tablet, desktop 1024 three-column; no
page-level horizontal overflow at 390/768/1440) **MUST** stay green, and `pnpm site:check`
**MUST** pass.

- Scenario: B102 overlap + parameter-table guards stay green
  - GIVEN the grouped `/docs/api`
  - WHEN `site/e2e/docs-api.spec.ts` runs (`pnpm site:test:e2e`)
  - THEN every `.param-table`/`.sig` block still sits left of the TOC at 1440 with no clip,
    `generate` still renders a parameter table with `schema` before `options`, and `Currency`
    still renders no table — all B102 assertions pass.
- Scenario (UI): grouped /docs/api reads as a clear mental model at desktop and mobile
  - GIVEN the production build of `/docs/api`
  - WHEN it is viewed in a real browser at desktop (1440) and mobile (390) (Playwright +
    designer/Chrome-DevTools-MCP pass at the review)
  - THEN the page presents visibly distinct, labelled group sections (a reader can orient:
    "Getting started", "Randomness", "World Explorer", … are visible section headings), the
    grouped TOC is visible on desktop and is the collapsed `<details>` disclosure on mobile
    (B114-R1), there is no page-level horizontal overflow at either width, and there is no
    `console.error`/`pageerror` during load.

## Out of scope

- **Adding the `group` field to the manifest/extractor** — it already exists (curation
  `group`, threaded by `extract.ts`, present on `ApiSymbol`). B115 renders it; it does not
  introduce it. (If a curation edit reveals the field were somehow not threaded, R1 covers
  re-threading — but ground truth says it is already present.)
- **Changing per-symbol prose, signatures, examples, or the TSDoc on `src/` exports** — B115
  touches grouping/order only. Prose remains the B102 TSDoc-sourced contract.
- **Collapsible/accordion group sections, intra-page group filtering, or a search box** —
  search is B104; B115 renders static grouped sections + a grouped TOC, no new interactive
  widget.
- **`/docs/relational`, `/docs/comparison`, and the other docs narrative routes** — untouched.
- **The B102 parity-guard machinery design** — reused as-is; B115 only feeds it grouped
  output and keeps it green.
- **The `architecture.md` Rules-section** — no new standing rule is expected (D5/D24/D21
  already cover this work). If the consolidated taxonomy is judged a standing convention, the
  rationale is logged to `wiki/decisions.md` and the **manager** promotes any rule — the
  spec-writer/implementer do not edit the Rules section.

## Open questions

1. **Final group taxonomy — names, order, and per-symbol assignment (Non-blocking;
   review/designer-pass item).** The eight-group set in Context is a concrete proposal curated
   into `scripts/docs/curation.ts`; the requirements are written against "the groups the
   curation layer defines", so the reviewer/designer can rename a group, reorder groups, or
   move a symbol between groups at the review pass without changing any `B115-R*` contract.
   Recommended **non-blocking**: a concrete taxonomy is proposed in the spec, the work can
   proceed against it, and the visual "reads as a clear mental model" judgement is exactly
   what the B115-R7 UI scenario + designer pass adjudicate. Not blocking — no answer is needed
   before the test-writer/implementer can start.

2. **Whether to consolidate the existing fine-grained groups or render them as-is
   (Non-blocking).** The current `CURATION` has 11 small groups; the proposal consolidates to
   8 broader ones for a cleaner mental model. If the maintainer prefers keeping the existing
   fine-grained groups and _only_ rendering them (no taxonomy change), every requirement still
   holds (they bind to "the curated groups", whatever set that is). Recorded; not blocking —
   the implementer curates to the proposed set unless the reviewer directs otherwise.

No blocking open questions.
