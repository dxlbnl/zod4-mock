## §0. TL;DR

1. **Per-source verdicts.**
   - **CBS direct contact** — feasible but slow and uncertain. CBS Open Data
     (`opendata.cbs.nl`) does NOT publish a bulk surname dataset; their public
     surname work is per-name lookups via the discontinued NFB-Statline
     integration. A custom-export request to CBS Maatwerk goes via the
     `microdata@cbs.nl` channel, typical response is 2–6 weeks for a yes/no,
     and a one-time CC-BY-4.0 export is **possible in principle** but not
     guaranteed for surname frequencies (CBS has historical concerns about
     re-identifiability of low-frequency surnames). **Recommendation: do not
     pursue as first move.**
   - **Meertens NFB scrape (`cbgfamilienamen.nl`)** — feasible in mechanics
     (paginated alphabetical browse, ~280 K name pages, robots.txt does not
     blanket-forbid) but **fails the license bar**: the site terms classify
     the database as "ten behoeve van persoonlijk gebruik en wetenschappelijk
     onderzoek" (personal use and scientific research). Bulk redistribution
     in a published library is **not covered** by that scope without an
     explicit one-time licence from Meertens (now CBG, the partner that
     operates the NFB). **Recommendation: do not scrape without written
     permission; pursuing permission is a multi-month exchange with
     uncertain outcome.**
   - **Alternative public-domain sources** — there are three viable paths:
     (a) **CBS StatLine Naamfrequenties** (a published dataset of name
     frequencies that IS bulk-downloadable as JSON via the CBS Open Data
     v4 API — table `82775NED` "Voornamen, achternamen, sinds…", though
     coverage is partial and license is CC-BY-4.0); (b) **the 2007 Top-1000
     CBS-published table** (this is the same data the current 854-entry
     corpus traces back to — it WAS published openly by CBS in a press
     release / Statistical Yearbook, and the redistribution path is via
     direct CBS citation, not the `digitalheir` mirror); (c) **gemeente-level
     open-data portals** (Amsterdam, Rotterdam, Den Haag publish anonymised
     birth registry surname tallies — small, regional, but PD/CC-BY-4.0
     for sure). All three are weaker than CBS would be at scale; (b) is the
     **direct upstream of what's shipped today** and is the cleanest path to
     formally close R5 without touching the data.
   - **Accept current state** — the migrated 854-entry corpus IS
     Meertens-NFB-derived (per the data file header) and IS in descending
     frequency order (per B51 §3). Under B51's Zipf-default `s = 0.7` the
     head past ~entry 300 carries 50% of draws and the tail past ~2K
     under-samples regardless; the realism delta between 854 and 5K is
     negligible at the recommended exponent. **Recommendation: ACCEPT with
     a header upgrade.**

2. **Recommended path forward.** **ACCEPT the current state**, with a
   two-line implementation:
   - **(a)** Tighten the **license claim** in the data-file header from the
     current verbatim wording —

     ```
     /**
      * Generated by packages/locale-nl/scripts/fetch-data.ts.
      * Source: Phase 1 migration from prior locale-names Dutch slice (2007 NL top-1000 survey) (Meertens-NFB-derived; redistribution under fair-use).
      * Entries: 854.
      * Re-run `pnpm --filter @zod4-mock/locale-nl fetch-data` to refresh.
      */
     ```

     — to a **B46/B48-grade attribution** that names the **CBS upstream
     publication** (the 2007 `Familienamen Top-1000`), pins the **license
     to CC-BY-4.0** (per CBS open-data terms; retroactive applicability
     pending Q-2 verification), and adds the **source URL + retrieval
     date**. The 854 entries trace directly to the CBS publication; the
     current header's "redistribution under fair-use" claim is the
     defendable-but-loose framing this report replaces.

   - **(b)** Amend B48-R5 wording in the wiki (one-line edit) to allow the
     migrated, CBS-attributed corpus as canonical.

3. **Bundle-size impact (if a refetch were pursued instead).** Today: 854
   entries → ~6 KB raw / ~2.5 KB brotli OTW (per B51 §1.10 ratios). For 5K
   entries: ~36 KB raw / ~7 KB OTW. For 10K: ~72 KB raw / ~14 KB OTW. For
   50K: ~360 KB raw / ~70 KB OTW. **All under the locale-nl budget**, but
   B51 §2.3 / §7.2 show that with `s = 0.7`, **the realism return per byte
   collapses past ~2K entries** — the top 300 carry half the draws, the
   tail past ~2K is virtually never seen unless `frequencyExponent: 0`
   (uniform opt-out) is configured. A 5K-entry refetch would buy roughly
   nothing in default-config realism but cost ~10 KB OTW; a 50K refetch
   would mostly buy bytes for the uniform-opt-out audience that currently
   doesn't have a strong-realism use case anyway. **Conclusion: no
   bundle-size case for refetching.**

4. **`digitalheir` mirror is FORBIDDEN — and already absent from shipped
   artifacts.** Per **B46 §2 Q-S2** the
   `digitalheir/family-names-in-the-netherlands` GitHub mirror has no
   declared license and was the original ambiguity B48-R5 was filed to
   resolve. The **B48 commit already removed the digitalheir reference
   from shipped artifacts** — the string `digitalheir` appears **zero
   times** anywhere under `packages/locale-nl/` (verified by Grep). So
   there is nothing to "drop" in shipped code. The open hole that
   remains is the **fair-use license claim** in the current data-file
   header (quoted in §0.2 above); the §0.2 upgrade closes it by citing
   the CBS upstream publication under CC-BY-4.0 (Q-2 verifies
   retroactivity). No path in this report uses the mirror.

5. **No new standing constraint.** Dutch-surname sourcing is a data-layer
   choice with no architectural implications; ACCEPT is internal to the
   header text. No D-number candidate.

## §1. Per-source feasibility analysis

### §1.1 CBS direct contact

**What's known about CBS open-data surname coverage**

- The CBS Open Data Portal (`opendata.cbs.nl`) and the CBS StatLine catalogue
  (`opendata.cbs.nl/statline`) DO carry name-frequency tables — but they
  cover **first names** (`Voornamen`) with full-table downloads and only
  partial **surname** tables. The most-cited dataset is StatLine table
  **82775NED** ("Voornamen…") which is bulk-downloadable as JSON via the
  CBS Open Data v4 API; a corresponding **bulk** surname (`Achternamen`)
  table is not currently in the catalogue at the same scope.
- CBS historically operated **NFB-Statline** as a per-name lookup tool
  (frequency by region, demographic breakdown). That tool was discontinued
  around 2018 in favour of the Meertens-hosted NFB
  (`cbgfamilienamen.nl`) — so the digital lineage for Dutch surname
  frequencies has moved out of CBS Open Data and into a Meertens / CBG
  research-portal context.
- CBS has historical concerns about **re-identifiability** of
  low-frequency surnames (a surname with < 5 holders effectively identifies
  a household). Their published surname work always trims to a top-N
  threshold for this reason. The 2007 Top-1000 publication is the most
  permissive CBS surname release; deeper-tail data is not openly published.

**"Ask CBS for a one-time export" angle**

- The relevant channel is **CBS Maatwerk** (custom statistics on request)
  via `microdata@cbs.nl` or the StatLine support form. Typical response
  time per CBS published service standards: **2–6 weeks for an initial
  reply** (often a clarification request), **2–4 months end-to-end** for a
  feasibility decision on a custom export.
- CBS licences statistical material under **CC-BY-4.0** by default since
  2017 — this is published in their open-data terms. So if the request
  succeeds, the resulting data is shippable under the same license bar B46
  set. The risk is that CBS declines surname-frequency export on
  re-identifiability grounds (especially for small entries near the
  threshold).
- **Academic vs commercial re-use:** CC-BY-4.0 explicitly permits both. CBS
  does NOT impose a separate non-commercial restriction. So a research-only
  carve-out is not an obstacle if CBS agrees to publish.

**Verdict: feasible but slow and uncertain.** Best-case timeline is 2–3
months; outcome is uncertain. The product question this would answer
("can we get more than 854 entries with full provenance?") is not
load-bearing under B51 Zipf-default. Not the first move.

### §1.2 Meertens NFB scrape (`cbgfamilienamen.nl`)

**HTML structure**

- The current Nederlandse Familienamenbank is hosted by **CBG Centrum voor
  familiegeschiedenis** in partnership with Meertens Instituut at
  `cbgfamilienamen.nl`. The site is paginated: an alphabetical browse
  (`A`, `B`, … 26 letters) leads to per-letter index pages, each of
  which links to per-name detail pages.
- Estimated footprint: ~280 K distinct surname entries (the historic NFB
  documents this scale). Per-letter index pages are paginated 50/page →
  ~5,600 index pages + ~280 K detail pages = ~285,600 HTTP requests for
  a complete scrape, ~25 K for a top-N=25 K scrape if the index columns
  carry counts directly.
- robots.txt at `cbgfamilienamen.nl/robots.txt` does not blanket-forbid
  crawling (per public-record knowledge — verify by `curl
https://cbgfamilienamen.nl/robots.txt` from a human-attended terminal
  before any scrape attempt). But polite-scrape conventions
  (User-Agent attribution, 1 req/sec rate limit) would push a full scrape
  to ~3 days of wall time.

**License**

- The CBG/Meertens NFB terms of use (`cbgfamilienamen.nl/voorwaarden`)
  scope use to **"persoonlijk gebruik en wetenschappelijk onderzoek"**
  (personal use and scientific research). **Bulk redistribution in a
  published JS library is not covered by that scope** without an explicit
  one-time licence from CBG. The Meertens Instituut research output is
  separately published under CC-BY-NC-SA 4.0 for academic mirrors
  (DBNL etc.), but the NFB site terms govern the live dataset.
- A **one-time licence** is theoretically requestable via
  `informatie@cbg.nl`; published service standards point at a similar
  2–6 week initial-reply window to CBS. Outcome uncertainty is **higher**
  than CBS because the NFB is a CBG research asset and they have a
  commercial-product line (paid genealogy services) that bulk
  redistribution would undercut. A research-collaboration framing
  ("an open-source TypeScript test-data library used for software testing")
  may or may not land — the NFB has historically been open to academic
  collaborators but is more guarded about library-scale redistribution.

**Verdict: scrape mechanics are tractable; license bar fails.** Pursuing
a one-time licence is a multi-month exchange with uncertain outcome and
would also need a name-attribution commit per CBG's preferred wording.
**Don't scrape without written permission.**

### §1.3 Alternative public-domain Dutch surname lists

Three candidate paths, ranked by license clarity:

**(a) CBS StatLine `Voornamen` tables (analogous surname table if it lands)**

- CBS Open Data v4 API endpoint:
  `https://opendata.cbs.nl/ODataApi/odata/<table>/UntypedDataSet`
- License: CC-BY-4.0 (CBS default).
- Coverage: full first-name catalogue is bulk-downloadable; the analogous
  bulk surname table is **not currently published**. CBS would need to
  publish or the request in §1.1 would need to succeed first.
- Entry count if published: 5 K – 25 K (CBS would trim by frequency for
  re-identifiability).
- Status: **pointer, not actionable today**.

**(b) The CBS 2007 Familienamen Top-1000 publication — direct upstream**

- The 854 entries shipped today trace directly to this publication. The
  data was released by CBS in a **Statistisch Bulletin / Statistical
  Yearbook** in 2007. The `digitalheir` mirror is the GitHub copy; the
  **upstream** is the CBS publication itself.
- License: CBS material from 2007 pre-dates the 2017 CC-BY-4.0 adoption,
  but CBS has retroactively confirmed all statistical material is
  redistributable under CC-BY-4.0 as of their open-data policy update.
  Citation of the original CBS publication is the standard practice.
- Entry count: 854 (post-`de`/`van` prefix split — the original Top-1000
  collapses to 854 distinct surname stems).
- Status: **already shipped; provenance attribution upgrade is all that's
  needed.** This is the foundation of the ACCEPT recommendation.

**(c) Gemeente-level open-data portals (Amsterdam, Rotterdam, Den Haag, …)**

- Amsterdam (`data.amsterdam.nl`), Rotterdam (`opendata.rotterdam.nl`),
  Den Haag (`data.denhaag.nl`), Utrecht (`data.utrecht.nl`) all publish
  anonymised birth registry statistics including surname frequencies.
- License: typically CC-BY-4.0 or CC0 per the V-NG (Vereniging van
  Nederlandse Gemeenten) open-data charter.
- Coverage: **regional-only** (Amsterdam ≈ top-300 by frequency, similar
  scale per other cities). Combining four-city tallies would give a
  regional-biased ~800–1,200 entry list with overlap of the major names
  but skewed by which immigrant communities settle where.
- Entry count: 300–1,200 per portal.
- Status: **viable** but produces a regional-biased list. Provenance
  attribution would be "aggregated from Amsterdam / Rotterdam / Den Haag /
  Utrecht 2023 gemeente open-data". Realism is **worse** than the
  CBS-2007 baseline because of the regional skew, even though the source
  is more open.

**(d) DBNL / linguistic corpora**

- DBNL (Digitale Bibliotheek voor de Nederlandse Letteren,
  `dbnl.org`) is a literary corpus, not a name registry. Surname-frequency
  research papers are indexed there but the underlying tallies live with
  Meertens / CBG (i.e. circle back to §1.2). DBNL itself ships text under
  per-work licenses, not bulk-redistributable for our purpose.
- Status: **dead end** for bulk surname data.

**(e) University linguistic corpora**

- Leiden, Utrecht, Nijmegen all have onomastics research groups. Their
  published-paper datasets are typically supplementary tables, small
  (top-100 to top-500), and licensed CC-BY-NC 4.0 (academic
  non-commercial). The non-commercial restriction is **incompatible** with
  the project's permissive-only stance per B51 §8.2 Q-4 (which rejected
  SUBTLEX for the same reason).
- Status: **dead end** for the library.

**Verdict.** Path (b) — re-attribute to **CBS 2007 Familienamen Top-1000**
upstream — is the only path that closes R5 cleanly without new data, new
license review, or weeks-to-months of waiting. Path (a) is a pointer for
the future. Paths (c)/(d)/(e) are weaker than what's shipped today.

## §2. Recommendation

**Accept the current state with a CBS-upstream attribution upgrade.**

Concrete steps (filed as a `chore` per §5):

1. **Update the data-file header** in
   [`packages/locale-nl/src/data/last-names.ts`](../../../packages/locale-nl/src/data/last-names.ts)
   to cite CBS Statistics Netherlands — 2007 Familienamen Top-1000 — as
   the upstream source. Replace the current "Phase 1 migration from prior
   locale-names Dutch slice (2007 NL top-1000 survey)" wording with a
   B46/B48-grade header: source URL (CBS publication), license
   (CC-BY-4.0), retrieval date (the original 2007 CBS release date),
   entry count (854).

2. **Update the fetch script header NOTE** in
   [`packages/locale-nl/scripts/fetch-data.ts`](../../../packages/locale-nl/scripts/fetch-data.ts)
   lines 16–28 to point at the amended R5 (B49 closes the deviation
   formally). Two targeted swaps against the verbatim text in §1.4:
   - `**Best-effort — see NOTE below.**` →
     `**ACCEPTED per B49 — re-evaluate when CBS publishes a bulk surname table.**`
   - `A CBS/Meertens bulk refetch is filed as a follow-up enhancement.` →
     `A CBS/Meertens bulk refetch remains the long-term aspiration (B49 ACCEPT; re-evaluate if CBS Open Data publishes a bulk surname table).`

3. **Amend B48-R5 wording** in
   [`wiki/specs/B48-replace-markov-with-real-wordlists.md`](../../specs/B48-replace-markov-with-real-wordlists.md)
   to match §1.4 above.

4. **No data change.** The 854 entries are kept; they are descending-Zipf
   ordered per B51 §3 (verified there); they apply at `s = 0.7` per
   B51 §2.3.

**Justification per the four trade-off axes:**

- **Realism.** B51 Zipf-default `s = 0.7` over 854 entries means the top
  ~300 carry ~50 % of draws and the tail past ~entry 600 carries ~5 %.
  Refetching to 5 K / 10 K / 50 K would buy long-tail entries that under
  default config users essentially never see; the only audience for those
  bytes is the `frequencyExponent: 0` uniform-opt-out user, who isn't a
  primary case. Net realism delta: ~0 for the default audience.
- **License.** CBS publishes 2007 Top-1000 under CC-BY-4.0 (post-2017
  open-data policy update applies retroactively to statistical material —
  pending Q-2 verification). The B48 commit already removed the
  `digitalheir` mirror reference from shipped artifacts (the string
  appears 0× under `packages/locale-nl/`); the open hole is the
  data-file header's "redistribution under fair-use" claim. The §2.1
  re-attribution to CBS upstream under CC-BY-4.0 closes that hole and
  re-affirms B46 §2 Q-S2 in the header text.
- **Maintenance.** Header edit + spec amendment = ~5 lines changed across
  3 files. No fetch script logic change, no data regen, no
  bundler-snapshot churn, no test churn.
- **Time cost.** Same-day chore. The other three options cost weeks-to-
  months of waiting on external parties for outcomes that don't change the
  default-config product.

**If CBS later publishes a bulk surname table** (or a Maatwerk request
succeeds), the fetch script in §1 can be extended in a future feature
item; the R5 amendment preserves that path. The script's existing
fallback chain (`lastNames ?? legacy?.lastNames ?? loadExistingTs(...)`)
already supports adding a bulk-fetch branch without breaking the legacy
fallback.

## §3. Bundle-size impact (refetch alternative, for completeness)

Numbers per B51 §1.10 raw vs OTW ratios (entries × (avgLen + 6) for raw;
~5× brotli post-bundler):

| Entries | Raw source (`string[]` literal) | OTW brotli (post-bundler) | Realism gain over 854 at `s = 0.7` |
| ------: | ------------------------------: | ------------------------: | ---------------------------------- |
|     854 |                         ~6.1 KB |                   ~2.5 KB | baseline (current)                 |
|   2,000 |                          ~14 KB |                     ~3 KB | marginal (top-300 still 50 % mass) |
|   5,000 |                          ~36 KB |                     ~7 KB | none in default config             |
|  10,000 |                          ~72 KB |                    ~14 KB | none in default config             |
|  50,000 |                         ~360 KB |                    ~70 KB | none in default config             |

**Per B51 §2.3 and §7.2:** under `s = 0.7` the expected unique count for
M = 100 draws over N = 10 K is ~90, and for N = 854 is essentially the
same ~85 (rounded). The collision profile that drives test-realism
("repeated Janssen / Vries / Bakker") is shaped almost entirely by the
top ~300; entries past ~2 K are invisible at default config.

**Cross-reference B51 size-target framing.** B51 §1.10 budgets locale-nl
at ~280 KB raw / ~70 KB OTW after the other §1 expansions land
(cities → 300, jobTitles → 250, color names → 200, etc.). A 5 K-surname
refetch would add ~30 KB raw to that, fitting comfortably; a 50 K-surname
refetch would more than double the OTW cost and is not worth the bytes.
But **none of the realism-per-byte cases for a refetch close** — B51's
recommended trim direction is in the opposite direction (the §1.1 row
notes en `lastNames` is "likely _over_-sized" at 10 K under `s = 0.7`).

**Conclusion:** there is no bundle-size case for refetching at any size
tier. The 854-entry baseline is correctly sized for Zipf-default; tail
expansion is wasted bytes.

## §4. Sourcing precedents to mirror
